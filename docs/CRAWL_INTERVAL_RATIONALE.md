# 크롤링 주기(1시간) 설계 근거

> 발표 Q&A 대비 문서. "왜 크롤링 주기가 1시간인가? 근거가 있나?"라는 질문에 대한 답.
> 결론: 1시간은 **신선도 · 처리비용 · 사용자경험의 합리적 절충값**이며,
> 코드 수정 없이 `backend/config.yaml`(또는 `.env`의 `CRAWL_INTERVAL_HOURS`)로 조정 가능하다.

---

## 1. 한 줄 요약

크롤링 주기는 "더 자주 못 해서"가 아니라 **"더 자주 할 필요가 없어서"** 1시간으로 두었다.
API 한도에는 여유가 많지만, 신선도 체감·서버 처리비용·정보 과부하를 함께 고려하면
1시간이 균형점이다.

---

## 2. 근거 6가지

### (1) API 한도 — 제약이 아님
- 네이버 검색 API 일일 호출 한도: **25,000회**.
- 우리 사용량: 8개 카테고리 × 24회/일 ≈ **192회/일** (+페이징 일부).
- 한도의 **1% 미만**. → 1시간 주기는 API 제약 때문이 아니다. 더 자주도 기술적으로 가능하다.

### (2) 뉴스 신선도 vs 체감 — 더 자주 해도 차이가 작음
- 속보가 아닌 한, 동일 키워드의 검색 상위 결과는 분 단위로 거의 바뀌지 않는다.
- 10분 주기와 1시간 주기의 **사용자 체감 신선도 차이는 미미**하다.
- 우리 서비스는 "실시간 속보 알림"이 아니라 "개인화 큐레이션 피드"이므로 시간 단위 갱신이 적합.

### (3) 처리 비용 — 짧을수록 부하 누적
- 기사 1건 처리 = 본문 크롤링 + **Llama 요약(CPU에서 수 초)** + GPT 분류 + Ko-SBERT 임베딩.
- 주기를 짧게 하면 한 사이클이 끝나기 전에 다음 사이클이 겹쳐 CPU·LLM 부하가 누적된다.
- 1시간이면 한 크롤링 사이클이 다음 사이클 전에 여유 있게 완료된다.

### (4) 캐시 정합성 — Redis 5분 TTL과 조화
- 피드는 Redis에 5분 TTL로 캐싱된다.
- 크롤링 1시간 + 캐시 5분 조합이면, 사용자는 캐시 만료 후 대체로 최신 상태를 본다.
- 크롤링을 더 자주 해도 캐시 TTL 때문에 즉시 반영되지 않으므로 실익이 적다.

### (5) 사용자 경험 — 정보 과부하 완화
- 선행연구(언론과학연구 23권 3호, 2023)는 **정보 과부하·뉴스 피로가 뉴스 회피로 이어진다**고 본다.
- 과도하게 잦은 갱신은 오히려 피드를 끊임없이 뒤바꿔 피로를 유발할 수 있다.
- 적정 주기 유지가 안정적인 열람 경험에 유리하다. (근거 문서: `CREDIBILITY_RATIONALE.md` 논문 ②)

### (6) 업계 관행
- RSS 폴링·뉴스 애그리게이터의 통상 갱신 주기는 **15분~1시간** 수준이다.
- 1시간은 이 관행 범위의 보수적(부하가 낮은) 끝에 해당한다.

---

## 3. 정직한 한계와 조정 가능성

- 1시간은 데이터로 최적화한 값이 아니라 위 절충에 따른 **설계 기본값**이다.
- `backend/config.yaml` 의 크롤링 설정 또는 `.env` 의 `CRAWL_INTERVAL_HOURS` 로
  **코드 수정 없이** 주기를 바꿀 수 있다 (예: 30분, 2시간).
- 운영하며 신선도 요구와 서버 부하를 측정해 조정하는 것을 로드맵으로 둔다.
- 서버 기동 직후 1회 즉시 크롤링(`CRAWL_ON_STARTUP=True`)을 두어, 첫 사용자가
  1시간을 기다리지 않도록 했다.

---

## 4. 발표 Q&A 예상 답변

**Q. 크롤링 주기가 왜 1시간인가요? 그냥 정한 건가요?**
A. API 한도(일 25,000회)에는 여유가 많아 더 자주도 가능하지만, 속보가 아닌 한 신선도
체감 차이가 작고, 기사마다 LLM 요약·임베딩 비용이 들며, 피드 캐시가 5분이라 더 자주 해도
실익이 적습니다. 정보 과부하 측면에서도 적정 주기가 낫다고 봐서 신선도와 비용의 절충점으로
1시간을 기본값으로 정했고, 설정 파일에서 바로 조정할 수 있게 했습니다. 데이터로 최적화한
값은 아니라 운영하며 조정할 계획입니다.
